## 1. 技术选型说明

| 组件 | 选型 | 版本 | 选择理由 | 兼容性说明 |
|---|---|---|---|---|
| 语言 | C++20（启用 `-std=c++20`） | GCC 11.4+ | 设计书要求现代 C++ 特性（concepts/协程/structured binding）；GCC 11 已完整支持 C++20 协程（`std::coroutine_handle`） | WSL2 Ubuntu 22.04 自带 gcc-11，无需额外装 toolchain |
| 网络 | 自研 epoll Reactor（LT 模式起步） | Linux 5.1+ epoll | JD 硬要求"懂 epoll"，手写才能面试讲原理；不依赖 muduo/boost.asio | 仅 Linux 可编译（epoll 是 Linux 专属），Windows 下不编译 |
| KCP | libkcp 源码入仓 `third_party/kcp/` | 官方 kcp.c/kcp.h（纯 C，约 1000 行） | JD 硬要求 KCP；源码入仓避免链接依赖，面试时能直接翻 kcp.c 讲 conv/rcv_buf/snd_buf | MIT 协议，可商用 |
| 序列化 | Protobuf | v3.12+（Ubuntu apt 自带 libprotobuf-dev） | 设计书指定；登录包/房间包/帧同步包用 proto 定义，避免手写字节流 | 用 `protobuf_generate_cpp()` 自动生成 .pb.cc/.pb.h |
| 并发 | std::thread + std::atomic + 自研 SPSC 队列 | C++20 标准库 | 设计书明确不引 moodycamel；手写无锁队列是 JD 硬骨头 | 跨平台但本项目只跑 Linux |
| MySQL 客户端 | libmysqlclient（C API，比 mysql-connector-cpp 轻） | MySQL 8.x client | hiredis 是 C API，MySQL 也用 C API 保持风格一致；connector-cpp 是 C++ wrapper 但依赖重 | apt install libmysqlclient-dev |
| Redis 客户端 | hiredis（同步 API） | 1.0.2+ | 设计书指定同步封装；异步 hiredis 会把网络层搞复杂，本项目 QPS 不高同步足够 | apt install libhiredis-dev |
| 构建 | CMake | 3.22+（Ubuntu 22.04 自带） | 设计书指定；find_package 找 protobuf/hiredis/MySQL | 顶层一个 CMakeLists + third_party/kcp/CMakeLists.txt |
| 调试 | GDB 12 / Valgrind 3.19 / ASan / Linux perf | Ubuntu 自带 | 设计书要求全量跑 ASan/Valgrind/perf | ASan 用 `-fsanitize=address -fno-omit-frame-pointer` 编译开关 |
| 日志 | 自研 lockfree-logger（模块 B） | — | 设计书要求手写无锁日志，不引 spdlog/glog | 这是项目本身的模块，不是外部依赖 |

**明确不引入**：muduo、boost.asio、libuv、spdlog、glog、moodycamel、libco、boost.coroutine、gRPC、cURL、nlohmann/json（用 Protobuf 不用 JSON）。

## 2. 整体分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  运维层 (Ops)                                                 │
│  ├─ ASan / Valgrind 编译开关                                  │
│  ├─ perf top / perf record 热点采样                          │
│  └─ lockfree-logger 后台刷盘线程（模块 B）                    │
├──────────────────────────────────────────────────────────────┤
│  应用层 (Application)                                         │
│  ├─ game-gateway 登录网关进程（模块 C）                       │
│  │   └─ LoginService：收包→查 MySQL→写 Redis→回包            │
│  └─ kcp-battle-room 战斗服进程（模块 D）                      │
│      └─ RoomService：建房/加房/帧广播/断线重连                │
├──────────────────────────────────────────────────────────────┤
│  协议层 (Protocol)                                            │
│  ├─ Protobuf 编解码（Login.proto / Room.proto / Frame.proto）│
│  ├─ 4 字节大端包头 + Protobuf body 粘包分包                   │
│  └─ KCP 会话层（libkcp conv_id 管理，战斗服用）              │
├──────────────────────────────────────────────────────────────┤
│  网络层 (Net) —— 模块 A cpp-reactor-net                       │
│  ├─ EventLoop：单线程 epoll_wait 循环                         │
│  ├─ TcpServer：主线程 accept + worker 线程池（N 个 EventLoop）│
│  ├─ Channel：fd 事件分发（read/write/close）                  │
│  ├─ Buffer：std::vector<char> 自动扩容读写缓冲区              │
│  └─ FdGuard：RAII 封装 int fd，析构 close()                   │
├──────────────────────────────────────────────────────────────┤
│  存储层 (Storage)                                             │
│  ├─ MySQL 8：users 表（持久化账号）                           │
│  └─ Redis 7：session:{uid} / room:{id} / room:{id}:frame     │
├──────────────────────────────────────────────────────────────┤
│  接入层 (Client)                                              │
│  ├─ tcp_client_demo：命令行登录客户端（发 LoginReq）          │
│  └─ stress_client：压测脚本（打 Echo / 打房间）               │
└──────────────────────────────────────────────────────────────┘
```

**进程模型**：两个独立可执行文件
- `game_gateway`：监听 TCP 8001，跑 N 个 worker EventLoop（默认 N = CPU 核数-1）
- `battle_server`：监听 KCP 8002，跑 N 个 worker EventLoop
- 两个进程通过 Redis 共享数据（网关写 session，战斗服读 session 鉴权），不直接 RPC

**线程模型**：
- 主线程：accept 新连接，用 round-robin 把 fd 分发到 worker EventLoop
- 每个 worker 线程：跑一个独立 epoll_wait 循环，处理该 loop 上所有 fd 的读写事件
- 日志线程：1 个后台线程，从 SPSC 队列 pop 日志批量 write 到文件
- 战斗服广播：用 C++20 协程挂起等待下一帧 tick（100ms），不阻塞 EventLoop
- **数据库连接线程模型（P1-02/P1-03 修正）**：每个 worker 线程 `thread_local` 持有自己的 MySQL 连接和 hiredis Redis 连接，启动时按 worker 数 N 预建 N 套连接，全程无线程安全问题，不需要互斥锁。连接数 = worker 数（默认 3），MySQL/Redis 都扛得住。

## 3. 核心业务链路

### 3.1 链路 L1：客户端登录（M4）

```
[tcp_client]                [game_gateway:8001]           [MySQL]      [Redis]
     |                             |                          |            |
     |-- TCP connect ------------->|                          |            |
     |                             |-- accept, 分发到 worker loop
     |-- LoginReq{user,pwd} ----->|                          |            |
     |   (4B包头+pb body)          |                          |            |
     |                             |-- 粘包分包解出 LoginReq   |            |
     |                             |-- sha256(pwd+salt)       |            |
     |                             |-- SELECT * FROM users ---->|            |
     |                             |<-- row -------------------|            |
     |                             |-- 比对 password_hash     |            |
     |                             |-- SET session:{uid} token EX 7200 ---->|
     |                             |<-- OK --------------------------------|
     |                             |-- 组 LoginRsp{code,token,uid}           |
     |<-- LoginRsp ---------------|                          |            |
     |                             |-- 写日志（SPSC 队列）     |            |
```

**关键节点**：
- 输入：客户端 TCP 连上后发 `LoginReq{username, password}`
- 处理：网关在 worker loop 里同步调 MySQL（用 libmysqlclient C API，连接池预建 4 个连接），同步调 Redis（hiredis）
- 输出：客户端收到 `LoginRsp{code=0, token, uid}`；失败时 code=1001/1002 等错误码
- 鉴权：后续客户端发房间相关包必须带 token，网关校验 session:{uid} 存在

### 3.2 链路 L2：创建/加入房间 + KCP 帧同步（M5）

```
[client A]                [battle_server:8002 KCP]        [Redis]
    |                            |                            |
    |-- KCP connect ----------->|                            |
    |-- JoinRoom{room_id,token}>|                            |
    |                            |-- 校验 Redis session:{uid} |
    |                            |-- HSET room:{room_id} uid ready
    |                            |<-- OK ---------------------|
    |<-- JoinRoomRsp{members} ---|                            |
    |                            |                            |
    |-- 每 100ms 发 FrameInput{ |                            |
    |    room_id,uid,input} ---->|                            |
    |                            |-- RPUSH room:{id}:frame    |
    |                            |    input (LTRIM 留 100 条)  |
    |                            |<-- OK ---------------------|
    |                            |-- 协程 yield 到下一 tick    |
    |                            |-- 遍历房间成员，KCP 广播     |
    |<-- FrameBroadcast{frame,   |                            |
    |    inputs[]} ------------- |                            |
```

**关键节点**：
- 输入：客户端每 100ms 上报一次操作输入（就一个字节：方向键 0/1/2/3）
- 处理：战斗服在 EventLoop 里收到包，写 Redis 帧历史，然后用 C++20 协程 `co_await std::suspend_always` 挂起，等到下一个 100ms tick 醒来，遍历房间成员列表，把这一帧所有 input 打包广播
- 输出：房间内所有客户端收到 `FrameBroadcast{frame_no, inputs[]}`
- 广播延迟 P99 < 50ms（本机 KCP 不经过真实公网，主要是 EventLoop 调度延迟）

### 3.3 链路 L3：断线重连（M5）

```
[client A 断线]              [battle_server]            [Redis]
     |                           |                         |
     |-- KCP close ------------->|                         |
     |                           |-- 标记 uid 离线（不删成员）
     |                           |-- 启动 3 秒重连等待计时器
     |                           |                         |
     |  (3 秒内重连)              |                         |
     |-- KCP reconnect --------->|                         |
     |-- RejoinRoom{room_id,uid}>|                         |
     |                           |-- LRANGE room:{id}:frame|
     |                           |<-- 最近 100 帧 ---------|
     |<-- RejoinRsp{frame_no,    |                         |
     |    history[]} ----------- |                         |
     |                           |-- 把 uid 标记回 online   |
```

**关键节点**：
- 输入：客户端断线后 3 秒内重新 KCP 连上，发 RejoinRoom
- 处理：战斗服从 Redis 拉最近 100 帧历史，连同当前 frame_no 一起回包
- 输出：客户端拿到历史帧，本地回放追上当前帧
- 超过 3 秒未重连：战斗服把 uid 从房间成员里删掉（HDEL）

### 3.4 链路 L4：Echo Server 压测（M1/M6）

```
[stress_client N 个] --TCP--> [game_gateway 或独立 echo_server]
                                  |
                                  |-- 收到什么回什么（不查 DB）
                                  |-- 纯测网络层吞吐
```

- 这是模块 A 的自带示例，用来压 M1（1000 连接）和 M6（调优前后 QPS 对比）
- 不经过 Protobuf，不查 MySQL/Redis，纯网络层

## 4. 数据模型设计

### 4.1 MySQL：`users` 表

```sql
CREATE DATABASE IF NOT EXISTS cpp_game;
USE cpp_game;

CREATE TABLE IF NOT EXISTS users (
    id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    username      VARCHAR(64)  NOT NULL UNIQUE,         -- 登录名
    password_hash VARCHAR(128) NOT NULL,                -- sha256(salt+pwd) hex
    salt          VARCHAR(32)  NOT NULL,                -- 每用户随机 salt
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 种子数据（user1/123456, user2/123456）
INSERT INTO users(username, password_hash, salt) VALUES
('user1', '<sha256 hash>', 'random_salt_xxx'),
('user2', '<sha256 hash>', 'random_salt_yyy');
```

- 索引：`username` 已经是 UNIQUE 自带唯一索引，登录查询走这个索引
- 不做分区（demo 表就 2 行种子数据）
- 不做表关联（就一张表）

### 4.2 Redis Key 设计

| Key 格式 | 类型 | 内容 | TTL | 用途 |
|---|---|---|---|---|
| `session:{uid}` | string | token 字符串（随机 32 字节 hex） | 7200 秒（2 小时） | 网关登录成功后写，战斗服鉴权读 |
| `room:{room_id}` | hash | field=uid, value="ready"/"online"/"offline" | 无（房间生命周期内常驻） | 房间成员列表 |
| `room:{room_id}:frame` | list | 每帧操作输入 JSON（`{"uid":1,"input":3}`） | 无，LTRIM 保留最近 100 条 | 断线重连拉历史 |
| `room:next_id` | string | INCR 生成自增房间号 | 无 | 建房时分配 room_id |

**Redis 操作原则**：
- 所有 key 都带 `cpp_game:` 前缀（避免和本机其他项目撞 key）
- 战斗服不直接写 users 表，只读 Redis
- 网关不写 room 相关 key，只写 session

## 5. 接口规范（Protobuf 协议）

### 5.1 传输层格式（粘包分包）

```
+----------+---------------------------+
| 4 bytes  |  N bytes                  |
| big-endian| Protobuf serialized body |
| body_len |                           |
+----------+---------------------------+
```

- 包头：4 字节大端 uint32，表示后面 body 的字节数
- body：Protobuf 序列化后的字节流
- 收包逻辑：先收满 4 字节包头 → 解析 body_len → 收满 body_len 字节 → 反序列化
- 分包：Buffer 里可能粘了多个包，循环解直到 Buffer 剩余字节不够一个包头

### 5.2 Protobuf 消息定义（`proto/game.proto`）

```proto
syntax = "proto3";
package game;

// === 登录（TCP 网关 8001）===
message LoginReq  { string username = 1; string password = 2; }
message LoginRsp  { int32 code = 1; string token = 2; int64 uid = 3; string msg = 4; }

// === 房间（KCP 战斗服 8002）===
message CreateRoomReq { string token = 1; }
message CreateRoomRsp { int32 code = 1; int64 room_id = 2; }

message JoinRoomReq   { string token = 1; int64 room_id = 2; }
message JoinRoomRsp   { int32 code = 1; repeated int64 members = 2; }

message FrameInput    { int64 room_id = 1; int64 uid = 2; int32 input = 3; }
message FrameBroadcast{ int64 room_id = 1; int32 frame_no = 2; repeated FrameInput inputs = 3; }

message RejoinRoomReq { string token = 1; int64 room_id = 2; }
message RejoinRoomRsp { int32 code = 1; int32 frame_no = 2; repeated FrameInput history = 3; }
```

### 5.3 错误码规范

| code | 含义 | 触发场景 |
|---|---|---|
| 0 | OK | 成功 |
| 1001 | 用户不存在 | LoginReq 的 username 查不到 |
| 1002 | 密码错误 | password_hash 不匹配 |
| 1003 | token 无效 | 战斗服收到包但 Redis 里 session:{uid} 不存在 |
| 2001 | 房间不存在 | JoinRoom/RejoinRoom 时 room_id 不存在 |
| 2002 | 房间已满 | 成员数 > 50（M5 上限） |
| 3001 | 服务器内部错误 | MySQL/Redis 调用失败 |
| 4001 | 协议解析失败 | Protobuf 反序列化失败（P2-03 补） |
| 4002 | 包体超长 | body 超过 4MB 上限，直接断 fd（P2-03 补） |

### 5.4 鉴权规则
- 网关登录包（LoginReq）不需要 token
- 战斗服所有包（CreateRoom/JoinRoom/FrameInput/RejoinRoom）都必须带 token
- 战斗服收到包先 `GET session:{uid}`，不存在直接回 1003

## 6. 部署架构设计

### 6.1 拓扑（单机 WSL2）

```
WSL2 Ubuntu 22.04
├── mysqld        监听 127.0.0.1:3306
├── redis-server  监听 127.0.0.1:6379
├── game_gateway  监听 0.0.0.0:8001 (TCP)
│   └─ 主线程 accept + N=3 worker EventLoop
└── battle_server 监听 0.0.0.0:8002 (KCP/UDP)
    └─ 主线程 recvfrom + N=3 worker EventLoop
```

### 6.2 环境划分
- 只有一个环境：**开发/测试一体**（WSL2 本机，不做 staging/prod）
- 配置方式：编译期 constexpr（端口/MySQL/Redis 地址）+ 命令行 `--log_file` 等少量参数

### 6.3 高可用/扩缩容
- **本项目不做高可用**（单进程 demo，崩了手动重启即可）
- **不做弹性扩缩容**（设计书明确单进程多线程，不做微服务拆分）
- 面试时诚实说："生产环境会做 master-worker 多进程 + 心跳摘除，但本 MVP 范围不做"

## 7. 监控与运维

### 7.1 监控指标（模块 E 产出）
| 指标 | 采集方式 | 目标 |
|---|---|---|
| Echo Server QPS | stress_client 统计 | 调优后比初始高 ≥30%（M6） |
| 在线连接数 | game_gateway 内部计数器 | M1=1000 稳定 |
| 无锁队列写入 QPS | bench_queue 脚本 | ≥10 万条/s（M2） |
| KCP 广播 P99 延迟 | 客户端打时间戳 | <50ms（M5） |
| RSS 内存 | /proc/self/status | 5 分钟压测波动 <50MB（M1） |

### 7.2 运维手段（就是 JD 要的"故障排查能力"）
- **ASan**：编译加 `-fsanitize=address`，跑冒烟用例，内存泄漏/越界直接 abort 打栈
- **Valgrind**：`valgrind --leak-check=full ./game_gateway`，查 definitely lost
- **perf top**：CPU 热点采样，定位到具体函数
- **lockfree-logger**：所有关键路径都有日志，崩了能从日志复盘
- **GDB**：core dump 后 `gdb ./game_gateway core.xxx` 看栈

## 8. 技术风险与应对

| 风险 | 等级 | 影响 | 应对方案 |
|---|---|---|---|
| **手写 SPSC 无锁队列 memory_order 写错**，导致丢日志或数据竞争 | 高 | M2 不达标，面试硬骨头讲错 | ① 先写单线程版本（带 mutex）跑通业务 ② 再替换成无锁队列 ③ 用 TSan（ThreadSanitizer）跑一遍验证无竞争 ④ M2 压测脚本数条数对账 |
| **epoll LT 模式下写事件边缘触发问题**，导致 fd 一直可写 busy loop | 中 | CPU 100% | ① 只在 Buffer 有数据时才把 fd 挂到 EPOLLOUT  ② 写空后立刻 EPOLLOUT 摘除 ③ 用 perf top 看是不是卡在 epoll_wait |
| **KCP 定时器不调 kcp_update()**，导致 KCP 包不发出去 | 高 | M5 链路不通 | ① EventLoop 每次 epoll_wait 带 timeout=kcp_check 建议值 ② 每次醒来先调 kcp_update ③ 写个最小 KCP echo demo 先验证 |
| **WSL2 网络栈性能差**，压测数据达不到 M1/M6 | 中 | 数字不好看 | ① 压测和服务器都跑在 WSL2 本机（走 lo 回环，最快） ② 数字按 WSL2 实测写，不硬抄 Linux 物理机数据 ③ 面试时说明"WSL2 网络栈有损耗，物理裸机 QPS 会更高" |
| **MySQL 同步阻塞 worker 线程**，高并发登录时 EventLoop 卡住 | 中 | M4 响应 >50ms | ① 登录接口 QPS 不高（demo 就几个人登录），同步阻塞可接受 ② 预建连接池 ③ 面试时说"生产会把 MySQL 调用丢到异步线程池" |
| **C++20 协程 GCC 11 支持不完整** | 低 | 模块 D 协程写不出来 | ① 备选方案：用状态机回调写广播逻辑（退化为普通 Reactor 风格） ② 协程是加分项不是必须，写不出来不阻塞 M5 |
| **Protobuf 版本不匹配**，Ubuntu apt 的 protobuf 太老 | 低 | 编译不过 | ① apt install libprotobuf-dev protobuf-compiler ② CMake find_package 找版本 <3.12 就报错提示用户升级 |
