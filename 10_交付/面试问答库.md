## ① 选型对比

### Q1. 网络层为什么自己手写 epoll Reactor，而不用 libuv / asio 这类现成网络库？

- **30 秒版**：这个项目的目标就是练 JD 要求的 epoll 多路复用和 Reactor 模型。用现成库会把 epoll、事件分发、回调注册这些细节封装掉，我讲不清 EventLoop 和 Channel 怎么配合。约束是单人、两天、WSL 本机回环验证，不需要跨平台和成熟定时器，所以自己写了 EventLoop/TcpServer/Channel/Buffer，one-loop-per-thread，worker 线程 round-robin。代价是只做了 LT 模式，没有 ET 边缘触发，也没接成熟的定时器和连接池。
- **追问第 1 层**：one-loop-per-thread 和 one-loop-per-worker 怎么选的？
  - 每个 worker 线程持有一个 EventLoop，连接 accept 后 round-robin 分给 worker；没有用单 loop 扛全部连接，是想让多核分摊回调。
- **追问第 2 层**：LT 和 ET 为什么选 LT？
  - LT 写法出错率低，回调里没读完下次还会再报；ET 必须一次读干净，配合非阻塞循环读。项目时间紧，优先主链路稳定，ET 留作后续。
- **追问第 3 层**：惊群怎么处理的？
  - 没做多进程 accept 锁，单进程内多 worker 分发；跨进程惊群、SO_REUSEPORT 这套在本项目没做，是边界。
- **诚实说法**：epoll 框架是自研最小骨架，只覆盖 LT + round-robin；ET、定时器层级、连接池都是我下版本计划，当前没有实现。

### Q2. 战斗服为什么用 UDP + KCP，而不是继续走 TCP？

- **30 秒版**：帧同步这种场景对延迟和丢包敏感，UDP 更可控；TCP 有队头阻塞，一个包丢了后面都得等。所以战斗服用 UDP，在上面叠了一层自研最小兼容 KCP 收发，走 ikcp_send/input/recv。登录这种可靠请求走 TCP + Protobuf。另一方案全用 TCP 实现更简单，但移动网络下队头阻塞和切换表现差，不适合帧同步。约束是单人、两天、16GB 内存的 WSL2 回环环境，移植原版 libkcp 并做丢包调参收益低，所以先做最小兼容收发把链路跑通，可靠性深度留作下版本。
- **追问第 1 层**：KCP 解决了 UDP 的什么问题？
  - 在不可靠 UDP 上加可靠传输：重传、确认、滑动窗口。本项目收发链路跑通，L4 能收到 KCP 封装广播段。
- **追问第 2 层**：KCP 的重传和窗口参数调过吗？
  - 没有做丢包注入的端到端验证，ARQ 重传、滑动窗口这些可靠性深度是既定边界；third_party 是自研最小兼容实现，不是 skywind3000 原版。
- **追问第 3 层**：怎么证明 KCP 栈真的被驱动了，而不是裸 UDP？
  - broadcastOnce 改走 sess->send()（ikcp_send），回归收到 29 字节 KCP 段；回包保留 sendRaw 兼容 Python 裸 socket 测试客户端。
- **诚实说法**：KCP 可靠性我只验到收发链路通，丢包重传/窗口行为没在丢包环境测过；被追问细节时我会明确说这是边界，不背原版 KCP 参数。

### Q3. 日志队列为什么做成无锁 SPSC，而不是直接加互斥锁的 MPMC 队列？

- **30 秒版**：日志路径是生产者写、单个后台线程刷盘，模型上接近单生产单消费，用 std::atomic + memory_order 做 SPSC 环形队列可以避免每抢一把锁。队列做了缓存行对齐防伪共享，后台 AsyncLogger 批量刷盘。另一方案 mutex + 通用队列写法简单、支持多生产，但高并发下有锁竞争和上下文切换。约束是单人、两天在 16GB WSL2 上做 MVP，日志先按单消费者模型落地，多生产者通用队列留作下版本。
- **追问第 1 层**：为什么是 SPSC 不是 MPMC？
  - 这个实现按单生产者单消费者写的，head/tail 两个 atomic 位；如果真要多线程同时写同一个队列，需要换成 MPMC 或每线程队列，当前没压多生产场景。
- **追问第 2 层**：环形队列满了怎么办？
  - 当前是固定环形，满写策略和阻塞背压没有单独做健壮性处理，属于已知边界。
- **追问第 3 层**：无锁队列怎么验证不出错？
  - bench_queue 推一百万条 push/pop 对账，零丢失，吞吐 1220 万条/s；口径是纯内存对账，没把后台写盘计时算进去。
- **诚实说法**：无锁只在 SPSC 模型下验证过；多生产者、队列满背压、落盘丢不丢这些我没测，不声称通用无锁队列。

## ② 最难的问题（均来自失败日志 / 台账真实案例）

### Q4. 讲一个你排查过的并发竞态问题。

- **30 秒版**：战斗服的 `sessions_` 会话表，recvLoop 线程负责 insert/find，tickLoop 线程遍历/erase，两个线程并发读写同一个 std::map，是数据竞争（台账 Q-005，P1）。独立 Review 读代码时按线程模型梳理出来的。根因是 KcpServer 没加会话表锁。修法是加 sessions_mutex_，两个线程访问 sessions_ 的路径全部加锁，回归 regress_battle 通过。
- **追问第 1 层**：怎么发现的，跑出来崩了吗？
  - 这轮是代码审查发现的，不是线上崩出来的；当时 ASan 没开 TSan，没跑线程竞争检测，靠读线程模型定位。
- **追问第 2 层**：锁的粒度怎么把握？
  - 锁覆盖会话表的增删查，单次临界区只做 map 操作，不在锁里发网络包；广播遍历成员时持锁取快照，发送放锁外。
- **追问第 3 层**：怎么防再出现？
  - regress_battle 回归脚本覆盖建房/进房/发帧/重连；后续计划用 TSan 跑一遍关键路径，把竞态在编译/测试期暴露。
- **诚实说法**：这是单人项目代码 Review 阶段发现的，没有线上并发事故背景；TSan 我这轮没跑，线程安全证据主要是代码审查 + 加锁回归。

### Q5. 讲一个内存安全 / 悬空指针的问题。

- **30 秒版**：tickLoop 60 秒超时把会话 `delete` 掉之后，这个指针还留在 Room.members 里，下一轮 broadcastOnce 用它 sendRaw，踩到已释放内存（Q-006，UAF，P1）。定位是顺着会话销毁路径追下来的：超时只删了 KcpSession，没从房间成员表摘除。修法是 KcpServer 加 onSessionTimeout 回调，main_battle 注册，erase 前先把该指针从所有 Room.members 摘掉。
- **追问第 1 层**：用什么工具确认的？
  - 内存检测用 ASan 和 Valgrind，gateway/battle 三份 Valgrind 报告 definitely lost=0、ERROR SUMMARY 0；UAF 这例主要靠 Review 追指针生命周期。
- **追问第 2 层**：为什么会出现成员表留旧指针？
  - 销毁路径有两个出口：主动离开和超时断开；主动离开摘了成员，超时分支漏了摘除，两套路径没对齐。
- **追问第 3 层**：重连场景旧会话怎么处理？
  - 当前重复进房/重连的成员去重还没做（Q-016 deferred），重复 Join 会重复追加；UAF 摘除已防住悬空，但成员膨胀是下版本要补的。
- **诚实说法**：UAF 修复后回归通过、Valgrind 无 definitely lost；但成员不去重仍是已知 P2，我不会说成员表已经干净。

### Q6. 讲一次环境/编排导致的真实报错，你怎么定位和修的。

- **30 秒版**：step9 预走脚本首版没有在脚本内拉起中间件和服务，依赖上一个 WSL 会话残留的后台进程。WSL 跨会话会回收非 systemd 进程，新会话里 Redis 6380、gateway 8001、battle 8002 都不在了，pytest 连接被拒；收尾重启时 Redis 已经掉线，服务端 redis connect failed 直接 terminate（core dumped）。定位是看启动日志连接被拒，再核对端口进程发现进程没了。根因是脚本没自包含 ensure 中间件，重启前也没复核 Redis 在线。
- **追问第 1 层**：最后怎么改的？
  - 脚本开头改成自包含编排 services.sh start：ensure MySQL/Redis → 清场 → 起 gateway/battle；收尾重启前先确认 Redis 在线。没改业务代码。
- **追问第 2 层**：为什么 WSL 进程不保留？
  - MySQL 走 systemd 常驻；Redis/gateway/battle 是手动起的非 systemd 进程，跨 WSL 会话不保留，所以每个新会话必须先 start，不能赌上一次的后台进程还在。
- **追问第 3 层**：怎么防下次再犯？
  - 回归/预走脚本模板强制前置 services.sh start 段，preflight 先校验进程在线才允许跑用例；这条也写进了工作流改进建议。
- **诚实说法**：这是测试脚本编排问题，不是业务逻辑 bug；线上环境我没有真实事故处置经验，这套排查是本机自包含复现口径。

## ③ 再做一次（架构级改进）

### Q7. 登录链路现在的瓶颈在哪？再做一次你会怎么改？

- **30 秒版**：压测看到 10 并发 701.9 TPS，20 并发降到 533.4，50 并发持平 536.0，平均 RT 从 14.24 升到 93.68ms，20 并发后约 530 TPS 见顶，但服务端 CPU 快照只有 0.3%，没打满。归因是 3 个 worker 线程、回调内同步做 MySQL 查用户和 Redis 写 session、每请求短连接，瓶颈在线程数和同步阻塞，不是算力热点。再做一次：worker 数按核数校准，DB/Redis 访问异步化或接连接池，回调里只入队，写缓冲 + EPOLLOUT 批量 flush，再把压测客户端多线程化先解除客户端瓶颈。
- **追问第 1 层**：为什么判断不是 CPU 瓶颈？
  - M5 五十人房间 CPU 快照 0.3%（4 线程），登录三档错误率 0，RT 随并发线性涨而 CPU 没上去，更像排队和阻塞。
- **追问第 2 层**：异步化具体怎么落？
  - 请求回调只解析入队，由独立 IO/任务线程访问 DB/Redis，结果回写响应；MySQL 补连接池，避免每请求建连。
- **追问第 3 层**：短连接开销占多少？
  - 当前压测每请求新建 TCP，三次握手和回收计入 RT；这部分没单独拆解，是模型放大了建连成本，结论里如实标注。
- **诚实说法**：异步流水线和连接池是规划方向，当前代码还是同步阻塞模型；我没在异步模型上跑出过 TPS 提升数字，不预承诺能提多少。

### Q8. 房间状态现在存在内存里，再做一次你怎么把它持久化？

- **30 秒版**：当前房间、成员、帧历史都在内存 map，服务重启就丢（Q-013）；session 已经落 Redis，房间态还没有。再做一次：`room:{id}` hash 存成员，`room:{id}:frame` list 存最近帧（沿用现在最近 100 条截断），`room:next_id` 用 INCR 发房间号；重连时从 Redis 拉历史帧和成员。同时把成员表按 uid 去重，重复加入/重连替换旧会话指针，解决 Q-016 重复追加。
- **追问第 1 层**：为什么不全落 MySQL？
  - 房间成员和帧是高频读写、可丢失重建的数据，放 Redis 更合适；MySQL 只存账号这类持久账号数据。
- **追问第 2 层**：帧历史为什么截断 100 条？
  - 当前入队按最近 100 条截断，RejoinRoom 回传未广播历史；窗口大小是 MVP 取舍，没做按时间/数量的可调策略。
- **追问第 3 层**：持久化后一致性怎么考虑？
  - 这层我只规划到 Redis 读写，没做持久化与内存态的双写一致性、崩溃恢复细节；属于下版本设计，当前不展开承诺。
- **诚实说法**：房间态持久化是 deferred 项，代码里只有内存实现；Redis hash/list 的读写链路我还没写，讲的是设计方向。

## ④ 细节深挖

### Q9. 无锁队列的内存模型，memory_order 你是怎么选的？

- **30 秒版**：队列是 SPSC 环形缓冲，head/tail 用 std::atomic 整型。生产者写数据后 release 更新 tail，消费者读 tail 用 acquire，保证消费者看到的数据不早于 tail 更新；反向同理。头尾之间用缓存行对齐（alignas(64)）避免两个原子变量落在同一缓存行造成伪共享。
- **追问第 1 层**：为什么不用 seqlock 或 MPMC？
  - 场景是单生产单消费，SPSC 用两个 index 就够；MPMC 要处理多生产者竞争和 ABA，复杂度高，当前场景不需要。
- **追问第 2 层**：环形队列怎么判断空和满？
  - 对比 head 和 tail；满的判断留了一个空位区分满和空。
- **追问第 3 层**：memory_order 能不能更松？
  - 这部分我按 release/acquire 配对写的，再往 relaxed 收紧需要逐对验证可见性，当前没做更细的序分析。
- **诚实说法**：内存模型我能讲清 release/acquire 配对和伪共享处理；更弱的序、指令重排边界没有做形式化验证，深追我会承认只做到这个程度。

### Q10. 登录鉴权链路是怎么做的？怎么拦水平越权？

- **30 秒版**：登录成功后 MySQL 校验账号口令，Redis 写 `session:{uid}` = token，TTL 7190–7200s。建房、进房、重连三个入口都走 checkToken：从 Redis 查 `session:{uid}` 比对 token，不一致回 1003；token 和 uid 双向不匹配也回 1003。重复登录会覆盖旧 session，旧 token 随即失效。SQL 用预编译占位，8 条注入载荷实测全部 1001。
- **追问第 1 层**：token 怎么生成的？
  - 64 位十六进制，genToken 从随机源取字节；返回值和 fd 校验还不完善（Q-031 deferred）。
- **追问第 2 层**：重登为什么旧 token 会失效？
  - session key 按 uid 覆盖，第二次登录写新 token，旧 token 在 Redis 查不到对应会话，再用就 1003。
- **追问第 3 层**：帧上报入口也鉴权了吗？
  - 没有，这是已知边界（Q-017）：FrameInput 的 proto 里就没 token 字段，分支也没做房间归属校验；能发 UDP 到 8002 的包都能塞帧，8.5 复核维持 deferred。
- **诚实说法**：三个写操作入口鉴权做了并回归；帧输入入口鉴权是明确未做项，面试我会先讲这条边界，不等被问穿。

### Q11. MySQL 这边表结构、索引和口令存储是怎么处理的？

- **30 秒版**：users 表存账号和口令哈希，username 建唯一索引；查询用预编译占位符，不拼字符串。种子口令存的是 sha256(salt+password) 的哈希，不明文落库。L3 用例断言种子在册、哈希与 salt 非空、表 utf8mb4。
- **追问第 1 层**：为什么用唯一索引？
  - 登录按 username 查，唯一索引保证账号不重复，也挡住并发注册重名。
- **追问第 2 层**：哈希方案有什么不足？
  - 单轮 SHA-256 + 静态盐，不是 bcrypt/argon2 慢哈希，库表泄露后离线爆破成本低（Q-022 deferred）；下版本接慢哈希 + 每用户随机盐。
- **追问第 3 层**：连接怎么管理？
  - 当前连接参数硬编码在 MysqlConn/RedisConn（Q-023），没有连接池，每次连接的生命周期按请求/模块使用；配置外置和连接池都在 deferred。
- **诚实说法**：数据库这块我只做了单表 + 唯一索引 + 预编译，没有索引优化实战、没有慢查询分析；慢哈希和连接池是计划项。

### Q12. 压测拐点你是怎么定位的？用了什么工具？

- **30 秒版**：登录接口跑了 10/20/50 三档并发各 10s：TPS 701.9 → 533.4 → 536.0，平均 RT 14.24 → 37.54 → 93.68ms，错误率都是 0。20 并发后 TPS 基本不涨、RT 线性上升，判断处理能力见顶约 530。配合 M5 的 CPU 快照 0.3%，排除算力打满，归因为 worker 线程数有限、回调内同步阻塞 DB/Redis、短连接开销。
- **追问第 1 层**：为什么不用 perf 火焰图？
  - WSL2 内核和系统 perf 版本不匹配，perf record/report 不可用（Q-003）；改用 ps、top -H 线程级快照加拐点数据归因，没有函数级热点栈。
- **追问第 2 层**：压测客户端会不会自己就是瓶颈？
  - 会，压测客户端是单线程/多线程 Python 和自研 C++ 短连接客户端，服务端没被打满；结论里标注了客户端瓶颈，下版本先把客户端多线程化再测服务端上限。
- **追问第 3 层**：为什么不用 JMeter？
  - 协议是自定义 TCP + Protobuf 二进制，JMeter 原生 TCP Sampler 静态构造不了 pb body；JMX 只留了线程组骨架，实际用 Python 多线程压测。
- **诚实说法**：我没有出过热点函数火焰图，拐点归因是从并发数据 + CPU 快照 + 代码模型推的，不是 profiler 实证；这一点被追问时我会直接说明工具受限。
