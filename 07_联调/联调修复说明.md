## 2. 本轮问题处置（P2 deferred，未修代码）

### Q-016 · 成员表重复追加不去重（P2 → step8 健壮性）

- **现象**：同一 uid 重复 JoinRoom / RejoinRoom，`members` 反复 `push_back`，不去重。实测：建房后第 1 次 Join `members=[1,1]`，第 2 次 Join `=[1,1,1]`，两次 Rejoin 后最终 uid=1 出现 6 次（证据 `evidence/members_observe.log`）。
- **根因**：`main_battle.cpp:156`（JoinRoom）、`:197`（RejoinRoom）直接追加会话指针，未检查该 uid（或会话）是否已在 `room.members`；建房房主入列在 `:125`。
- **影响范围**：广播时向同一客户端重复投递、成员表语义膨胀；**不丢帧、不错帧、不崩溃**。UAF 已由 Q-006 修复（超时摘除后才 `delete`），本问题不引入内存安全风险。主链路单次路径（建房 → 他人进房 → 断线重连一次）members 正确。
- **去向**：step8 健壮性补齐——members 按 uid 去重；重复加入/重连时替换旧 KcpSession 指针而非追加。
- **为何本步不修**：边界场景，非主链路阻塞；按 step7 规则只修来源阶段=7 的 open P0/P1，P2 标 deferred 留档。

### Q-017 · FrameInput 入口无鉴权 / 无房间归属校验（P2 → step8.5 / step8）

- **现象**：type=5 FrameInput 分支（`main_battle.cpp:163-172`）不调 `checkToken`，也不核对 uid 是否在该房间 members；任何能发 UDP 到 8002 的包都可向任意 `room_id` 塞帧。
- **根因**：Q-008 鉴权修复只覆盖 Create/Join/Rejoin 三入口，帧输入入口漏覆盖；MVP 内网 demo 优先打通帧同步。
- **影响范围**：内网 demo 无外部流量，不构成可利用的外部风险；属健壮性与安全边界。
- **去向**：step8.5 安全扫描复核 + step8 健壮性补齐——FrameInput 补 token 校验与房间归属/uid 一致性检查。

### 4.2 断言口径

- 不只断 `code=0`：每条断言至少核对一个关键字段（uid / token 长度与字符集 / members 集合 / room_id 自增 / history 帧数与首帧 uid+input / frame_no / TTL / Redis session 值）。
- L4 广播：裸 Python 客户端只见 KCP 封装段（段长 >0），不强解 `FrameBroadcast` pb（既定边界，见清单 §4.1）；帧入队正确性由 L5.2 积压帧内容（uid/input 一致）侧面核对。
- C1 一致性：`mysql_before.txt` 与 `mysql_after.txt` diff 一致，证明登录/战斗链路只读 users 表、未写库。
- C2 一致性：重复登录后 Redis session 与新 token 一致，旧 token 建房回 1003，新 token 建房回 0。
