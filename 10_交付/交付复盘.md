## 2. 项目整体完成情况与基线逐条达成

### 2.1 总体结论

设计书 §2 MVP 最小可用场景（两客户端 → 网关 Protobuf 登录 → MySQL 校验 → Redis 写会话 → 进同一战斗房 → KCP 帧同步广播 → 断线 3 秒内重连恢复）已端到端跑通，L4 E2E 用例通过；8 条 JD must_have 均有代码落点，其中 5 条真实落地、3 条降级（详见 §5）。项目按纯后端基础设施定位交付，未越界写战斗数值/匹配/支付/前端。

### 2.3 核心问题与根本原因

1. **M6 调优收益不足（Q-001）**：echo 回显路径无用户态内存/字符串分配热点，微优化收益为个位数百分比；瓶颈在回环 RTT、epoll 唤醒粒度、回调内同步 read/write 模型与单线程压测客户端，非局部字符串/容器微调可突破（`perf-report.md` §6/§7.1）。
2. **M8 代码量不足（Q-002）**：MVP 聚焦网络/并发/性能三个 JD 硬点，业务模块从简；未以注释或生成代码凑行数，如实记债。
3. **房间态未持久化（Q-013）**：房间/成员/帧历史当前为内存态，服务重启即丢；Redis hash/list 持久化路径未落地。
4. **登录吞吐拐点（Q-019）**：3 worker 线程 + 回调内同步阻塞 DB/Redis，20 并发后 TPS 见顶约 530；未上异步化与连接池。
5. **工具链环境受限（Q-003/Q-020/Q-021）**：WSL 内核与 perf 版本不匹配无火焰图；裸 UDP 客户端解不出应用层帧时间戳，广播 P99 不可测；L3 未用 Testcontainers。

## 6. 选题准确率复盘（对照 step00 预测）

> 适用条件：项目来自 step00，根目录同时有 `00_原始项目描述.md`（设计书）与 `00_JD对账表.md`，本节执行。

### 6.1 工作量预估

- 设计书 §8 预估 **6.5 人天**（A 1.5 / B 1 / C 1.5 / D 2 / E 0.5）；实际按轮次统计（非人天口径）：11 轮，4 次人工卡点。AI 协作系数因无墙钟计时未记录。
- 模块偏差：**模块 D（KCP 战斗服）** 是实际最花时间的部分（房间态/重连/广播协程/KCP 封装多处返工与边界标注），与设计书「主项目、2 人天」判断一致；**模块 E（压测调优）** 被低估——设计书假设 perf 可调出热点、QPS 提 30%，实际 WSL perf 不可用且回环模型瓶颈不在用户态，M6 未达标。
- 卡点预测：设计书未预测卡点次数；实际 4 次人工卡点，集中在评审、冒烟确认、安全放行、验收。

### 6.2 技术选型翻车与踩坑项

- **翻车/降级**：
  - **perf 工具链**：WSL 内核与系统 perf 版本不匹配，`perf record/report` 不可用，出不了火焰图（Q-003），被迫降级为线程级快照。
  - **JMeter**：私有 TCP+Protobuf 二进制协议，JMeter 原生 TCP Sampler 无法静态构造 pb body；降级 Python 多线程压测（`perf-report.md` §1）。
  - **KCP 实现**：third_party 用自研最小兼容实现，非 skywind3000 原版；收发链路通，但 ARQ/重传/窗口未端到端验证。
- **比预想顺利**：epoll Reactor、SPSC 无锁队列、Protobuf 编解码、MySQL 预编译、Redis session 均一次打通；M1 千连接 300s 零断开、M2 百万零丢失达标。

### 6.3 硬骨头模块复核

| 设计书判定 | 实际难度 | 结果 |
|---|---|---|
| 模块 B 无锁队列（内存模型/屏障/伪共享） | 真硬，但一次做对 | ✅ M2 达标，百万零丢失 |
| 模块 A epoll 多路复用（LT/ET、惊群、负载均衡） | 中等，比预想顺利 | ✅ one-loop-per-thread 线程池落地 |
| 模块 D KCP 集成（定时器/收发缓冲对齐） | 半硬：收发通，可靠性深度验证被迫留边界 | ⚠️ ARQ 重传/滑动窗口未端到端验证 |
| 模块 E 性能调优（perf 找热点改 string_view/预分配提 30%） | 最难，且未达成 | ❌ M6 1.046 未达 1.30；瓶颈非局部微调可解 |

### 6.4 JD 覆盖率复核

- 设计书声称 must_have 8/8=100%；实际代码/架构有落点的 **8/8**，其中 **5 条真实落地、3 条降级**（§5）。
- 面试时讲不深的边界点：KCP 重传/窗口细节、Redis 房间态持久化、连接池、M6 调优收益、perf 火焰图——这些在简历话术里必须如实降级，不能按「硬实现」深讲。

### 6.5 被砍掉的 JD 词复核

设计书 §3 主动砍掉：游戏战斗数值/技能/BUFF、前端、Web 后台、跨服分布式、Docker、gRPC、SSL/TLS、WebSocket、HTTP/REST。复核：**无砍错**——本岗为纯 C++ 后端基础设施岗，被砍项与岗位方向无关；其中 Docker 一项因 WSL 裸跑既定取舍，compose 模板仅留骨架（未启用），不属于被保守误砍。

### 6.6 反哺动作

- **不可实现清单更新**：见 `docs/个人项目不可实现清单.md` 第五节，已补 C++ 后端类避坑条目（WSL perf 受限、JMeter 打不了私有二进制协议、自研最小 KCP 与原版边界、回环压测客户端瓶颈）。
- **估算基线校准**：后续 C++ 服务端选题，模块 E 性能调优预估须计入「工具链受限 + 回环模型瓶颈」风险；不要在设计阶段承诺 ≥30% QPS 提升目标，除非压测客户端与中间件先解除瓶颈。
- **避坑清单**：见下节流程改进建议，每条对应真实失败记录。

## 8. 流程改进建议（每条对应真实失败记录）
